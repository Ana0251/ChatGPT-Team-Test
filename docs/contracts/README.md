## Compatibility and conventions
- All requests/response JSON UTF-8 with English API property names, Persian presentation only in frontend. ISO Gregorian dates, UTC event timestamps and exact IRR string amounts.
- **CSRF bootstrap and rotation:** Anonymous `GET /auth/csrf` sets random, opaque, short-lived pre-auth `hesabyar_pre_session` cookie (HttpOnly; Secure; SameSite=Lax; Path=/) and returns an HMAC-bound token linked to pre-session, origin and expiration; response has `Cache-Control: no-store`. Browser sends the bound cookie, same-origin `Origin` and `X-CSRF-Token` on login/activation. For authenticated users `GET /auth/csrf` binds to the authenticated session. On login rotate to a fresh session identifier, clear pre-session, invalidate old CSRF and retrieve a new CSRF before any further mutation. Logout revokes session and CSRF. Missing/expired/mismatched CSRF or invalid Origin => `403 CSRF_INVALID`; fetch a fresh token and never blindly replay unsafe requests. Session cookies cannot be read from JavaScript; CSRF tokens must not be persisted in localStorage/logs.
- **First user, no public registration endpoint:** A trusted private operator runs an audited, restricted one-time provisioner (out-of-band, not a public HTTP API) creating a pending first owner and pending initial company. No default credentials. A 256-bit random, single-use setup token is delivered privately to verified target email, only hashed token stored, expires within 15 minutes. Anonymous `POST /auth/activate` with bound CSRF, setup token, and strong password activates this existing pending owner; token consumed atomically, password stored via approved adaptive hash; this does not create login session. First user then calls login. Repeated/expired setup tokens fail generically; onboarding is never a super-admin grant.
- **Invitation policy:** `POST /companies/{companyId}/members` is invitation-only for **existing or not-yet-existing emails**, returns `202 Invitation` without raw token, never immediate membership. Only company owner/admin may invite; only a current company owner may invite another company-scoped owner (including a new email), with no super-admin role. Each hashed 256-bit one-use invitation token binds normalized recipient email, company and role; expires within 48 hours, rate limited, delivered privately (not logged). Existing internal users sign in and call CSRF-protected `POST /auth/invitations/accept`; server compares invite email to verified session email. New invitees use pre-auth CSRF and `POST /auth/invitations/activate` with token and strong password to create an internal account and acquire *only* invited membership. If email already belongs to an account, activation rejects and requires authenticated acceptance; invitations cannot reset passwords or bypass membership. Expired/reused/duplicate invitations yield generic conflict and must be reissued by authorized inviter. This is a proposed account-provisioning workflow subject to manager security review.
- Tenant context is URL-scoped /companies/{companyId} wherever relevant; backend validates membership with each action. No default-cross-company reporting.
- Standard error: `{error:{code,message,details?,request_id}}`. 400 malformed business input, 401 unauthenticated/expired, 403 insufficient role or CSRF, 404 absent or nonvisible resource (do not leak cross-tenant IDs), 409 duplicate/period/state/idempotency conflict, 422 structural/domain validation; avoid leaking internals.
- IDs are UUIDs; list endpoints use page/page_size (no cursor in V1.0) with stable ordering and deterministic ties by id. Business rows are immutable once posted; request header Idempotency-Key mandatory on posting/reversal. Header CSRF token on all mutations.
- Roles: owner/admin can maintain memberships and company; owner/admin/accountant can maintain fiscal/accounts/drafts and post/reverse under policy; viewer read-only. Closing fiscal periods is owner/admin only. API enforces roles, not just UI.
- **Trial balance totals:** `TrialBalanceRow` represents an individual account; `TrialBalanceTotals` has only six IRR totals (opening_debit/credit, debit/credit movement, closing_debit/credit) and has **no** account identity. At level=general/subsidiary roll up each posted leaf once; at level=detail use the complete postable-leaf set: DETAIL leaves PLUS SUBSIDIARY accounts with no DETAIL child. Return actual account_name and account_level per row. Never sum parent and child in the same total. `totals` are computed over **all filtered accounts before pagination**, not just `items` on the selected page; `total` is unpaginated matching row count. Date filters are `[from_date, to_date)`; openings include posted lines before `from_date`; movements within window; reversals count as posted, drafts excluded. F1 movement Dr=Cr=1,200,000; F2 movement Dr=Cr=1,400,000, regardless of page number. Opening and closing totals reconcile via signed account balances. F3 tenant isolation remains mandatory.
- Posted-only reports include reversals, exclude drafts, and provide money as strings. Running totals sign convention: debit-positive; credit-negative; credit side displayed separately where needed.
- Proposed reference response paging: `{items:[],page:1,page_size:50,total:0}`. Max page size 100. Error `request_id` correlates sanitized logs without exposing credentials.

- **Owner invitation:** Newly activated account may become the **invited owner of exactly the specified company**, if a current owner issued the bound single-use token and server checks authority/role/email/company at acceptance; never global admin. admin may not invite owner. No instant membership at invitation.
