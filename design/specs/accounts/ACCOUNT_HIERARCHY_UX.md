# H-19 — مشخصات اجرایی تجربه کدینگ حساب‌ها

**وضعیت:** SPECIFIED / RUNTIME_NOT_TESTED؛ نسخه فریم‌ورک 1.3.0؛ مصوبه `APP-HESABYAR-W2-PHASE1-ENTRY-20261116-001` و ارجاع Manager در PR #70، کامنت `6910825905`.  
**مبنای ثابت API:** OpenAPI `1.0.0-rc.4`، Git blob `f57de031224e21f09253642c210a778a60683711`. **Design foundation:** H-17؛ **company context:** H-18. این سند طراحی است، نه پیاده‌سازی H-09.

## هدف و معماری اطلاعات
کاربر دارای عضویت معتبر شرکت بتواند کدینگ چهارسطحی را مشاهده کند و با مجوز مناسب حساب بسازد، نام/فعال‌بودن را اصلاح کند یا حسابِ بدون استفاده و بدون فرزند را حذف کند. مسیرهای اصلی:
`شرکت مجاز ← کدینگ حساب‌ها ← انتخاب سطح/والد ← افزودن حساب ← بازبینی کد کامل و وضعیت ثبت‌پذیری ← ثبت ← مشاهده در فهرست`.
مسیر ویرایش: `فهرست ← جزئیات حساب ← تغییر نام یا وضعیت فعال ← تأیید ← پاسخ سرور`. مسیر حذف: `جزئیات ← بررسی پیام پیامد ← تأیید حذف ← حذف تنها در صورت پذیرش سرور`.

## سلسله‌مراتب و محدودیت ساختاری
- ساختار `group → general → subsidiary → detail`؛ حساب group ریشه و بدون والد، general فرزند group، subsidiary فرزند general، detail فرزند **دقیقاً یک** subsidiary است. والد و شناسه شرکت باید از رکوردهای معتبر همان شرکت باشند.
- `code` یک **رشته** ۱ تا ۶۴ کاراکتر؛ صفرهای سمت چپ مثل `000001` باید حفظ شوند. `full_code` فقط خروجی محاسبه‌شده سرور و برای نمایش LTR-isolated؛ در UI قابل ویرایش نیست. کد کامل باید در دامنه شرکت یکتا باشد؛ از روی `code` کلاینت، یکتایی را قطعی فرض نکن.
- `name` رشته ۱ تا ۲۰۰ کاراکتر؛ `active` Boolean، مقدار پیش‌فرض ورودی true. `postable` فیلد محاسبه‌شده **فقط خروجی**؛ هرگز به‌عنوان فیلد ویرایشی ارسال نشود.
- حساب group/general برای ثبت سند انتخاب‌پذیر نیست؛ subsidiary فعالِ بدون فرزند detail می‌تواند ثبت‌پذیر باشد، detail leaf فعال نیز می‌تواند ثبت‌پذیر باشد. تغییر تعداد فرزندان، active و وضعیت سرور ممکن است `postable` را عوض کند؛ UI از پاسخ تازه API پیروی کند.
- تغییر والد، کد، سطح یا ساختار در `PATCH` مصوب نیست: تنها `name` و `active` قابل ویرایش‌اند. کنترل «جابجایی حساب»، «تغییر کد» و «ادغام حساب» در H-19 طراحی نمی‌شود.
- حذف حساب دارای فرزند، سند قطعی یا استفاده محافظت‌شده ممنوع است. دلیل دقیق باید از پاسخ سرور معتبر باشد؛ آزمون واقعی «حساب مصرف‌شده در سند قطعی» تا اجرای Posting در حوزه بعدی **NOT_TESTED** است.

## ساختار صفحه و اجزا
1. **Context header:** نام شرکت و نقش مجاز از H-18؛ راه برگشت به انتخاب شرکت؛ تغییر شرکت با اخطار ترک داده و واکشی دوباره، نه جابه‌جایی داده فهرست قبلی.
2. **Toolbar:** عنوان «کدینگ حساب‌ها»، دکمه «افزودن حساب» صرفاً برای نقش مجاز، شمارش رکوردها از `AccountPage.total`، کنترل صفحه `page` و تعداد در صفحه `page_size`. API برای فهرست تنها فیلتر `parent_id` دارد؛ «جست‌وجوی سراسری سروری» و مرتب‌سازی سفارشی **قرارداد نشده‌اند**؛ از وعده آن‌ها اجتناب شود. درخت سلسله‌مراتب با واکشی صفحه‌بندی‌شده فرزندانِ والد انتخابی ساخته می‌شود؛ تمام فرزندان را از یک صفحه فرض نکن.
3. **List/Tree:** ردیف نام حساب، `code` (رشته)، `full_code` (LTR، قابل کپی دقیق)، سطح فارسی گروه/کل/معین/تفصیلی، فعال/غیرفعال، قابل ثبت/غیرقابل ثبت با متن و آیکن. عمل «بازکردن فرزندان» مستقل از «انتخاب حساب» است؛ مسیر پدران قابل بازگشت.
4. **Create panel:** فیلدهای سطح (انتخاب صریح)، والد (بر اساس سطح؛ برای گروه فاقد والد)، کد جزء، نام، فعال؛ پیش‌نمایش بصری کد کامل صرفاً **نمونه غیرقطعی** تا پاسخ سرور. هشدار «کد حساب شامل صفرهای آغازین است و به همان صورت ثبت می‌شود» در صورت نیاز.
5. **Detail/read:** شناسه حساب فقط در متن فنی مجاز و بیدی ایزوله، نام/سطح/والد/کد/کد کامل/active/postable؛ `POST` ایجاد، `PATCH` فقط نام/فعال و `DELETE` فقط در حدود قرارداد. غیرمجازها را با دلیل قابل فهم نشان بده؛ مخفی‌سازی دکمه جایگزین کنترل 403 سرور نیست.
6. **Delete confirm:** نام و کد کامل همان حساب، متن خطر حذف، «انصراف» + «حذف حساب»؛ بارگذاری مانع کلیک تکراری؛ موفقیت فقط پس از 204؛ خطای 409 `ACCOUNT_IN_USE` بدون حذف نمایشی.

## مجوزها و بازبینی دسترسی
- مشاهده فهرست/جزئیات تنها برای عضویت معتبر همان شرکت. ایجاد/ویرایش/حذف طبق توضیح عملیات API برای `owner/admin/accountant`؛ `viewer` فقط خواندنی. برای هر عمل مجوز واقعی روی سرور بررسی می‌شود.
- اگر عضویت منقضی یا لغو شود: 401/403/404، محتوای دارای داده شرکت قبلی پنهان و context بازبینی می‌شود. 404 هیچ نشانه‌ای از وجود حساب در شرکت دیگر نمی‌دهد.
- `CSRF_INVALID` ⇒ فقط یک GET تازه CSRF، سپس پیام و **ارسال مجدد با اقدام انسانی**؛ هیچ POST/PATCH/DELETE به‌شکل خودکار replay نمی‌شود. نتیجه نامعلوم شبکه نباید موفق/ناموفق قطعی نشان داده شود.

## واکنش‌گرایی و دسترس‌پذیری
- ۳۶۰ و ۳۹۰: یک ستون، padding ۱۶، هر کارت با نام و کد کامل و دو نشان متنی active/postable؛ فرم به‌صورت بخش عمودی، عملیات بحرانی بدون قطع‌شدن، دکمه‌های >=۴۴px. درخت چندسطحی به جای تورفتگی عمیق، breadcrumb عمودی و دکمه مستقل «زیرحساب‌ها» دارد.
- ۶۰۰: دو پنل فقط اگر هر کدام خوانا و بدون برش باشند؛ در غیر این صورت تک‌ستون. ۱۰۲۴/۱۲۸۰: درخت یا فهرست در سمت راست و جزئیات در سمت چپ با سقف عرض محتوا ۱۲۸۰.
- راست‌به‌چپ با `lang=fa`، کدهای لاتین/رقمی با `bdi dir=ltr` و **بدون تبدیل رقمِ شناسه**؛ ترتیب فوکوس با DOM منطقی؛ `Enter/Space` روی فعال‌کننده، `Escape` خروج از dialog، بازگرداندن فوکوس به منبع، `aria-expanded` و `aria-controls` برای باز/بسته کردن درخت.
- پیام خطا کنار فیلد با `aria-describedby` و خلاصه خطا با `role=alert`؛ فونت Vazirmatn/Tahoma و رنگ توکن‌های H-17؛ ۴٫۵:۱ متن، ۳:۱ حالت‌های غیرمتنی، ۲۰۰٪ zoom، reduced motion. این‌ها **معیار طراحی‌اند؛ تست مرورگر/صفحه‌خوان اجرا نشده است**.
