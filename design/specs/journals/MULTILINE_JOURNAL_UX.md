# H-19 — طراحی اجرایی سند حسابداری چندردیفی

**Status:** SPECIFIED / RUNTIME_NOT_TESTED. **Contract:** OpenAPI `1.0.0-rc.4`, blob `f57de031224e21f09253642c210a778a60683711`. **پیش‌نیاز تصویب‌شده:** H-17، H-18. هیچ اجرای H-10/H-11 یا frontend مجاز یا انجام‌شده فرض نمی‌شود.

## نقش، معماری صفحات و جریان کار
- **فهرست اسناد:** `شرکت انتخابی و سال مالی ← اسناد حسابداری`؛ شمارش و صفحه‌بندی `JournalPage`، فیلترهای قراردادی `status=draft|posted` و `fiscal_year_id`؛ فیلتر «نام حساب/شرح» و مرتب‌سازی دلخواه سروری خارج از rc.4 هستند، مگر صرفاً روی رکوردهای دریافت‌شده با برچسب محدود بودن دامنه.
- **سند جدید:** `ایجاد سند ← انتخاب سال مالی مجاز ← تاریخ ثبت شمسی ← شرح کلی ← افزودن سطرهای متعدد ← بررسی جمع بدهکار/بستانکار و هشدار ← ذخیره پیش‌نویس`. اگر ورودی ناقص یا نامتوازن باشد، دکمه **«ذخیره پیش‌نویس» فعال می‌ماند** تا وقتی قالب و شناسه‌های ارائه‌شده مطابق قرارداد باشند؛ هر ردیف ناقص به‌صورت `DraftLine` ذخیره می‌شود.
- **بازکردن پیش‌نویس:** `GET Journal ← نمایش warnings و totals واقعی سرور ← افزودن/ویرایش/حذف/جابجایی ظاهری سطرها ← ذخیره مجدد PUT`. تغییر ترتیب سطرها باید با `line_index` هشدارها به ترتیب فعلی **پس از پاسخ ذخیره** نگاشت شود؛ شناسه پایدار خط در `JournalDraftInput` تعریف نشده و از UI نباید `line_id` ساختگی به API ارسال شود.
- **ثبت قطعی:** `ذخیره پیش‌نویس ← بازبینی داده‌ها و وضعیت دوره ← دکمه «ثبت قطعی» ← تأیید اثر غیرقابل‌ویرایش ← POST /post با Idempotency-Key ← پاسخ status=posted`. فقط **پاسخ واقعی سرور** موفقیت قطعی را ثابت می‌کند. پیش‌بینی تراز/اعتبار سمت رابط صرفاً راهنمای غیرقطعی است.
- **پس از ثبت قطعی:** جزئیات فقط‌خواندنی، `voucher_number`، `posted_at`، وضعیت `posted`، جمع‌ها و خطوط ثابت؛ دکمه ویرایش/حذف وجود ندارد. مجوز استفاده از برگشت سند با اختیار سرور تعیین می‌شود.
- **برگشت سند:** `سند قطعی ← «برگشت سند» ← پنجره مستقل با تاریخ برگشت شمسی و علت اجباری ← بازبینی اثر و تأیید ← POST /reverse`. عملیات سند برگشتی جدید و مرتبط ایجاد می‌کند، نه ویرایش سند اصلی. پیوند سند اولیه `reversal_of_id`، نشان `reversed` و نمایش شماره/ID در صورت مجاز بودن ارائه شود.
- **حذف پیش‌نویس:** فقط روی `status=draft` با تأیید آگاهانه `DELETE /journals/{journalId}`؛ برای سند قطعی API حذف معتبر ندارد.

## ساختار صفحه و اجزا
1. **هدر زمینه:** شرکت + نقش + سال مالی فعلی و وضعیت دوره از H-18؛ تغییر شرکت/سال با اخطار فرم ناتمام، پاک‌سازی state/selection وابسته و واکشی مجدد. داده شرکت قبلی به شرکت جدید انتقال یا کپی خودکار نمی‌شود.
2. **هدر سند:** عنوان «سند حسابداری»، badge متنی «پیش‌نویس» یا «ثبت قطعی»، تاریخ `posting_date` شمسی به‌صورت یک تاریخ واقعی، انتخاب `fiscal_year_id` بر اساس شرکت، شرح کلی. `voucher_number` تا وقتی از سرور موجود نیست `— / تخصیص‌نیافته`؛ شماره فرضی یا تولید client ممنوع.
3. **جدول سطرها:** «ردیف»، «حساب»، «شرح ردیف»، «بدهکار (ریال)»، «بستانکار (ریال)»؛ دکمه افزودن/حذف سطر تنها در پیش‌نویس. Picker حساب از `GET /accounts` با صفحه‌بندی و context شرکت، تنها `postable=true` و `active=true` قابل انتخاب برای ثبت قطعی؛ کد کامل عین رشته LTR با حفظ صفرها. اگر حساب از زمان انتخاب تغییر کرد، خطای سرور تعیین‌کننده است.
4. **منطقه جمع و هشدار:** `total_debit`, `total_credit` دقیق به ریال، هر دو در پاسخ `Journal` اجباری‌اند **حتی در Draft ناقص**. تفاوت جمع در UI می‌تواند محاسبه دقیق از رشته/Decimal باشد؛ هرگز JS float/Number. Warningهای `JournalWarning[]` با کد/ردیف/فیلد/متن فارسی و آیکن؛ فرق «هشدار ذخیره‌پذیر» با «خطای مانع ثبت قطعی» با تیتر روشن مشخص می‌شود.
5. **نوار اعمال:** `ذخیره پیش‌نویس` (اولویت اصلی هنگام ویرایش)، `ثبت قطعی` (عمل پرریسک با تأیید جداگانه)، `انصراف`، `حذف پیش‌نویس` به‌صورت تخریبی و دور از ثبت قطعی. دکمه پست در صورت فقدان اطلاعات ظاهری می‌تواند راهنمای کمبود نشان دهد، اما **نباید با غیرفعال‌کردن همیشگی پیش‌نویس ناقص امکان ذخیره را از بین ببرد**.
6. **صفحه read-only:** اطلاعات و ترتیب خطوط بدون امکان ویرایش؛ نشان «برگشت‌خورده» صرفاً از پاسخ `reversed=true`؛ عملیات برگشت دوباره ممنوع تا پاسخ سرور/وضعیت مجاز، نه صرفاً شرط ظاهری.

## قواعد عملیاتی و اعتبارسنجی بدون اختراع business logic
- مبلغ ورودی JSON با `Rial` canonical `^(0|[1-9][0-9]{0,19})$` به‌صورت **string ASCII** و غیرمنفیِ ریال صحیح، حداکثر ۲۰ رقم، بدون اعشار/منفی/توان/float. ورودی UI می‌تواند ارقام فارسی/عربی را بپذیرد و در زمان ارسال به ASCII canonical تبدیل کند؛ ورودی نادرست مثل `۱.۵` یا ۲۱ رقم به شکل خطای فیلدی نشان داده شود، نه گرد/بریده شود.
- سطر کامل برای ثبت قطعی: `account_id` صحیح، از **دو مقدار debit/credit دقیقاً یکی >0** و دیگری `"0"`. حداقل دو ردیف معتبر و جمع بدهکار=جمع بستانکار، جمع مثبت؛ حساب قابل ثبت و فعال، تاریخ داخل دوره باز، سال و شرکت و مجوز معتبر با کنترل سرور. این‌ها راهنمای کاربرند؛ مجوز نهایی فقط response معتبر `POST /post`.
- `DraftLine.account_id` ممکن است null یا حذف‌شده باشد، `debit/credit` اختیاری‌اند؛ برای سطر ناقص **مقادیر ساختگی `"0"`** در payload جایگزین «خالی» نشود. خروجی warn صرفاً بعد از ذخیره یا دریافت از API است؛ خطای ساختاری/مقدار نامعتبر 422 می‌تواند ذخیره را متوقف کند. شناسه حساب ارائه‌شده حتی در Draft باید scoped و معتبر باشد.
- در هر درخواست امن POST/PUT/DELETE، CSRF/Origin معتبر و cookie نشست H-05 لازم است؛ بعد از 403 `CSRF_INVALID` فقط GET یک‌باره برای token تازه و **بدون replay خودکار mutation**. پس از 401 session و login مجدد، شرکت/سال/دوره بازبینی و اقدام انسان مجدد لازم است.
- `Idempotency-Key` در `/post` و `/reverse` لازم است؛ کلید به شرکت/کاربر/عمل/اثر انگشت درخواست وابسته است. برای **همان بدنۀ تغییرنکرده** پس از وضعیت نامطمئن، فقط پس از بررسی وضعیت سرور و بازبینی انسان ممکن است همان کلید استفاده شود؛ برای payload جدید کلید تازه. کلید نباید در URL یا متن رابط یا telemetry آشکار شود. `409 DUPLICATE_POST` و `409 IDEMPOTENCY_CONFLICT` نباید به ارسال بی‌پایان منجر شوند.
- `PERIOD_CLOSED` یا `DRAFT_DATE_OUTSIDE_PERIOD` با انتخاب دوره معتبر/تاریخ صحیح رفع شود. تاریخ شمسی در UI → Gregorian ISO `YYYY-MM-DD` در API؛ بازه دوره `[start_date,end_date)` و انتهای نمایش‌شده `end_date-1` روز میلادی و سپس تبدیل به شمسی. مرز کاری `Asia/Tehran`، زمان رخداد `posted_at` UTC و بدون جعل وضعیت بسته/باز.
- منطق role/scope شرکت توسط سرور اجرا می‌شود؛ viewer در تجربه پیش‌فرض read-only است، انجام عملیات فقط طبق مجوز واقعی سرور. UI از endpointهای غیرمجاز نتیجه‌ای درباره وجود منبع شرکت دیگر نشان ندهد.

## RTL، ۳۶۰ تا ۱۲۸۰ و دسترس‌پذیری
- **۳۶۰/۳۹۰px:** سطرها به کارت‌های عمودی شماره‌دار تبدیل می‌شوند؛ حساب، شرح، بدهکار و بستانکار هرکدام label دارند؛ باز کردن Picker در محدوده viewport؛ جمع‌ها زیر هم با متن «بدهکار/بستانکار» و unit. دسترسی همیشگی به «ذخیره پیش‌نویس» بدون پوشاندن هشدار و ورودی؛ هیچ truncation مبلغ ۲۰رقمی، هر سطر امکان اسکرول افقی محدود/متن‌شکنی کنترل‌شده دارد، بدون اسکرول افقی کل صفحه.
- **۶۰۰px:** فرم و سطرها به جدول قابل اسکرول محلی یا کارت با حداقل ارتفاع ۴۸px در هر سطر؛ toolbar wrap؛ ترتیب DOM و فوکوس حفظ شود.
- **۱۰۲۴/۱۲۸۰px:** جدول مالی با ستون‌های ثابت معنادار، header sticky، پنل جمع و هشدار جدا؛ حداکثر پهنا ۱۲۸۰؛ ترتیب ستون‌ها مطابق عنوان فارسی و بدون جابجایی تصادفی debit/credit.
- `lang=fa`, `dir=rtl`؛ کد حساب، UUID و شناسه‌ها در `bdi dir=ltr`؛ ارقام نمایشی فارسی با گروه‌بندی `٬` و unit «ریال»، مقادیر raw API همیشه ASCII string؛ کد `000001` نباید `1` شود.
- همه ورودی‌ها label مستقل و `aria-describedby`، خطای مرتبط با سطر، اعلان تغییر جمع پس از ذخیره و خطای قطعی به صورت `role=alert`؛ Tab از هدر به سطرها سپس جمع/دکمه‌ها، افزودن سطر فوکوس روی حساب سطر جدید، حذف سطر فوکوس روی مجاور معنادار؛ هنگام باز شدن dialog فوکوس محبوس و هنگام بسته شدن به trigger بازگردد. مسیر تنها با صفحه‌کلید، اندازه hit area >=۴۴px، کنتراست متن ۴٫۵:۱ / غیرمتنی ۳:۱، zoom ۲۰۰٪ و reduced-motion معیار طراحی‌اند، نه تست اجراشده.
- به‌کارگیری رنگ/تایپوگرافی H-17 `design/tokens/foundations.json`، بدون تعریف برند یا توکن تازه. تم روشن و تاریک باید همسانی محتوایی داشته باشند و تغییر تم داده/فوکوس را پاک نکند.
